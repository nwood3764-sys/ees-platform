# OSM Fixer — Build Instructions (Claude Code session brief)

**Give this whole file to a Claude Code session.** It is written as a task brief
*to that session*, but it is plain enough for a non-engineer to follow along. The
goal is a self-serve tool that repairs DOE Asset Score **OpenStudio models
(`.osm`)** so they translate and run cleanly in EnergyPlus — and, above all,
**fixes everything that is broken with the water heaters**, which is the #1 thing
blocking these models from running today.

A working scaffold already exists in this same folder
(`audit-template-builder/osm-fixer/`). **You are not starting from zero — you are
finishing and hardening it, then deploying it.** Read every file listed in
§3 before writing any code.

---

## 1. Mission

Energy Efficiency Services (EES) receives OpenStudio models (`.osm`) generated by
the DOE Asset Score / OpenStudio pipeline. As delivered, most of them **fail to
translate to EnergyPlus and will not run** — the failures are concentrated in the
**service water-heating (SWH) system**. Today someone has to hand each model to
Claude one at a time to repair it. That does not scale.

**Build a tool that takes one or more `.osm` files, repairs them, and returns
models that are guaranteed runnable** — verified by forward-translating to IDF
with **zero translation errors** before the file is ever handed back. Non-technical
staff must be able to use it in a browser: drop files → download fixed files.

Definition of done for a single model: `openstudio` forward-translation produces
**0 errors**, HTML tabular output is enabled, and no water heater was lost in the
process.

---

## 2. Why these models don't run (the water-heater problem)

The DOE-generated `.osm` files carry SWH plumbing that EnergyPlus rejects. Two
shapes show up:

1. **Central water heater with a recirculation loop.** There is a `PlantLoop`
   whose name contains "recirc" — a hot-water recirculation loop that fails in
   the translated IDF (bad node/branch topology, orphaned pumps/setpoint
   managers). The main SWH loop and its water heater are fine; only the recirc
   loop is the problem.

2. **Per-unit standalone water heaters, no circulation lines.** Some buildings
   have **no central water heater** — every dwelling unit has its own
   `WaterHeaterMixed`, and **there are no circulation loops at all**. Here the
   failure is *not* a recirc loop; it is usually the water heater's **ambient
   temperature reference** (see below) multiplied across dozens of units, and/or
   per-unit loop objects that don't translate.

The two recurring root-cause failure modes, regardless of shape:

- **`WaterHeaterMixed` ambient temperature points at a `ThermalZone`.** When the
  referenced zone doesn't translate cleanly (or the indicator is set to "ThermalZone"
  with a zone that E+ chokes on), translation fails. Fix: set the ambient
  temperature **indicator to "Schedule"** and point it at a **constant 21 °C
  schedule**, and reset the thermal-zone reference. This is safe and is the single
  most important water-heater fix.

- **`Schedule:File` objects with dangling external-CSV references.** These
  reference CSV files that don't exist at run time and crash EnergyPlus. Remove
  them.

**Hard guardrail:** never delete a water heater. When you remove a recirc loop,
check the set of `WaterHeaterMixed` objects before and after — if removing the
loop would have deleted a heater, **abort and leave the model unchanged** with a
clear error. Documentation/energy modeling must never silently lose equipment.

`service/repair.py` already implements, in order:
1. Remove all `Schedule:File` objects.
2. Remove `PlantLoop`s whose name contains "recirc" (with the water-heater
   guard — aborts if a heater would be lost).
3. Pin every `WaterHeaterMixed` ambient temperature to a constant 21 °C schedule
   and reset the thermal-zone reference.
4. Enable HTML results: `OutputControl:Table:Style = HTMLandColumns`, the
   `AllSummary` report, and monthly end-use meters (so a run produces the
   `eplustbl.htm` the Audit Template Builder consumes).
5. **Forward-translate the model to IDF and record the error list** — the summary's
   `runnable` flag is `true` only when there are **0 errors**.

`service/app.py` exposes `GET /health` → `{"ok":true,"sdk":"3.7.0"}` and
`POST /fix` (multipart, one or more `.osm`; returns the corrected file, or a
`.zip` + `repair_summary.json` for multiple; single-file summary also comes back
in the `X-OSM-Fixer-Summary` response header).

**Your job is to harden the repair against real files (especially the per-unit
water-heater shape), then deploy the service and wire the front end to it.**

## 4. Build plan (phased, each phase independently shippable)

### Phase 0 — Stand it up and prove the baseline works
- In `service/`, create a venv, `pip install -r requirements.txt`, run
  `python app.py` (serves on :8080). Hit `GET /health` → expect
  `{"ok":true,"sdk":"3.7.0"}`.
- Get **2–3 real broken `.osm` files** from EES (ask the person who handed you
  this file). Include at least one **central+recirc** model and one **per-unit
  standalone water heater** model (e.g. the 36515-style building: no central
  heater, no circulation lines).
- Run each through `POST /fix` (or call `repair_osm()` directly:
  `python repair.py in.osm out.osm` prints the JSON summary). Record which ones
  come back `"runnable": true` and which still list `translate_errors`.

### Phase 1 — Close every water-heater failure mode
For each model that still has `translate_errors`, **diagnose the actual error
text** and extend `repair.py` to fix that class of failure. Do NOT band-aid a
single file — fix the *category* so it never recurs. Likely additions beyond
what's already there:
- Per-unit water heaters whose ambient indicator/zone still trips translation
  (make the ambient-schedule fix apply to *all* `WaterHeaterMixed`, which it
  already does — verify it actually runs on the multi-unit models).
- Orphaned SWH loop objects on per-unit setups (pumps, setpoint managers,
  connector lists, plant equipment operation schemes) that reference removed or
  missing nodes.
- Any `Schedule:File` the DOE export leaves behind (already removed — confirm).
- Weather-file path: **preserve it unchanged** (do not repoint it). The model
  keeps its `WeatherData/USA_*.epw` reference; running the model is done later by
  EES in OpenStudio with that EPW present.

**Rule:** the only acceptable exit for a repaired model is `translate_errors == []`.
If a model cannot reach zero errors, return a clear, specific error naming the
object/failure — never a silently half-fixed file.

### Phase 2 — Batch + summary UX
- `POST /fix` already handles multiple files → `.zip` + `repair_summary.json`.
  Make sure the summary clearly reports, per file: SDK note (version-translated?),
  `schedule_file_removed`, `recirc_loops_removed`, `water_heaters_fixed`,
  `idf_objects`, `translate_errors`, `runnable`.
- Front end (`frontend/index.html`): show each file's result (✓ runnable / ✗ with
  the error), and the download. Keep it dead-simple.

### Phase 3 — Deploy (see §6) and wire the front end
- Deploy `service/` as a container; copy the live URL into
  `frontend/config.js` (`window.OSM_FIXER_URL`).
- Deploy `frontend/` (Netlify) — or, the intended end state, fold this upload UI
  in as a **new tab inside the Audit Template Builder** at
  `ees-audit-template-builder.netlify.app`, with the deployed service as its
  engine.

## 5. How to diagnose a new water-heater failure (the method)

When a model comes back with `translate_errors`, don't guess — read them:

1. Load the model in Python and forward-translate:
   ```python
   import openstudio
   m = openstudio.model.Model.load("in.osm").get()   # or VersionTranslator for older
   ft = openstudio.energyplus.ForwardTranslator()
   ws = ft.translateModel(m)
   for e in ft.errors():   print("ERR :", e.logMessage())
   for w in ft.warnings(): print("WARN:", w.logMessage())
   ```
2. The error text names the object/field. Water-heater failures almost always
   trace back to: an ambient **ThermalZone** reference, a **Schedule:File**, or a
   **plant-loop node/branch** that references something removed. Map the error to
   one of those and fix the *class* in `repair.py`.
3. Re-translate. Iterate until `ft.errors()` is empty.
4. Add a short comment in `repair.py` documenting the failure mode and the fix,
   so the next person/model benefits. Treat `repair.py` as the accumulated
   institutional knowledge of "what's broken with these models."

Work with the SDK object graph (as `repair.py` does), **never** text-edit the
`.osm` — objects cross-reference by handle and text surgery corrupts them.

## 6. Deploy runbook (browser-only, no command line) — Render

This matches a non-technical setup; Render builds the Docker engine straight from
the repo. (`README.md` has the same steps plus a Fly.io alternative.)

1. **Account** — render.com → Get Started → **Sign in with GitHub** (the account
   that owns `nwood3764-sys/ees-platform`). Authorize Render, include the
   `ees-platform` repo.
2. **Create** — **New +** → **Web Service** → pick `ees-platform` → Connect.
3. **Settings:**
   - Name: `osm-fixer`
   - Branch: `master`
   - Root Directory: `audit-template-builder/osm-fixer/service`
   - Language/Runtime: **Docker** (auto-detected once Root Directory is set)
   - Instance Type: **Free**
   - Env vars: none required. Later set `ALLOWED_ORIGIN` to the Audit Template
     Builder origin to lock CORS.
4. **Deploy** — first build is ~5–10 min (installs the OpenStudio library). Wait
   for **Live** (green).
5. **Test** — open `https://osm-fixer-xxxx.onrender.com/health` → expect
   `{"ok":true,"sdk":"3.7.0"}`. Copy that base URL.
6. **Wire the front end** — put the URL in `frontend/config.js`
   (`window.OSM_FIXER_URL = "https://osm-fixer-xxxx.onrender.com";`) and deploy
   `frontend/` to Netlify (publish dir `.`, no build).

Free-tier notes: the service **sleeps after ~15 min idle** and takes ~50 s to
wake on the next request (then it's fast). The front end should show a "waking
the engine…" state so users don't think it hung.

## 7. Testing & acceptance criteria

- `GET /health` returns `{"ok":true,"sdk":"3.7.0"}`.
- For every real EES sample (both central+recirc and per-unit standalone shapes):
  `POST /fix` returns a corrected model with **`runnable: true`** and
  **`translate_errors: []`**.
- **No water heater is ever lost.** Count `WaterHeaterMixed` before/after; the
  recirc removal aborts (with a clear error) rather than deleting a heater.
- The repaired model still points at its original weather file (unchanged).
- HTML output is enabled (`HTMLandColumns` + `AllSummary` + monthly meters), so a
  later OpenStudio run produces `eplustbl.htm`.
- Multiple-file upload returns a `.zip` with a per-file `repair_summary.json`.
- **The corrected file actually opens and runs in OpenStudio** — confirm with EES
  on at least one real building end-to-end before calling it done.

---

## 8. Guardrails / non-negotiables

- **Never delete a water heater.** Abort-and-report instead.
- **Never text-edit the `.osm`.** SDK object graph only.
- **Never repoint or strip the weather file.**
- **Zero-error gate is the definition of runnable.** Do not hand back a model
  that still lists translation errors; return a specific error instead.
- **Fix the category, not the one file.** Every new fix goes into `repair.py`
  with a comment, so the knowledge compounds.
- Keep the front end trivially simple (drop → fix → download). No accounts, no
  config UI beyond the service URL.
